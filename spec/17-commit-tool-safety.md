### 9.10 Commit Generation & Agent Tool Safety

Cross-cutting requirement consolidating three concerns exposed by two production
incidents in a test worktree (`pi-mulligan-hack`, 2026-08-08 → 08-11):

1. **Mis-attribution.** Every PRP work-item commit (46 of 49) was stamped
   `Co-Authored-By: Claude <noreply@anthropic.com>` by a **hardcoded literal**
   in `formatCommitMessage`, even though the pipeline was running the `pi`
   harness on z.ai `glm-5.*` models — no Anthropic model was involved. The
   first three commits were clean only because they were hand-authored spec
   commits that bypassed that code path.
2. **Remote-side mutation.** An agent flipped the GitHub default branch of the
   target repository to the test worktree's branch, using an **unguarded shell
   tool** plus the host's `repo`-scoped `gh` credentials.

Both are properties of this pipeline's commit + tool surface. §9.10.1 makes
commit-message generation identity-transparent by delegating to the solved
`stagecoach` tool; §9.10.2 enforces the (already-existing) §5.1 identity-
transparency rule with a structural guard so it cannot regress again; §9.10.3
scopes agent tool access and bans remote-mutating operations from every agent.

#### 9.10.1 Commit-Message Generation (stagecoach delegation, message-only)

**Problem.** The descriptive commit message was generated by an **in-process
re-implementation** of stagecoach (the section literally labeled "STAGECOACH
(LLM COMMIT-MESSAGE GENERATION)"). A re-implementation drifts: it had acquired
a hardcoded `Co-Authored-By: Claude` trailer that the real `stagecoach` tool —
identity-transparent by design (its FR-39a invariant + structural guard) — would
never emit. Re-implementing a solved problem is what produced incident (1).

**Requirement.** The descriptive commit message is generated by delegating to
the **`stagecoach` binary** — the same tool exposed by the user's
`git stagecoach` alias — not by an in-process agent. Concretely:

- **Shipped with this tool (no external runtime dependency).** `stagecoach` is
  declared as an npm **dependency** via the `stagecoach-ai` package, whose
  `postinstall` downloads the correct per-platform native binary (goreleaser
  cross-builds linux/darwin/windows × amd64/arm64) into
  `~/.stagecoach/versions/<ver>/<plat>/`. `npm install hacky-hack` therefore
  brings `stagecoach` along transitively: **no separate install, no `PATH`
  lookup, no Go toolchain for end users** (Go is needed only at `stagecoach`'s
  release). The pipeline resolves the binary via the dependency's resolved path
  and execs it directly as an **argument vector — never `sh -c`** — forwarding
  argv and inheriting stdio/env.
- **Scope: message-only.** `stagecoach` is invoked as
  `stagecoach --dry-run --single`: `--dry-run` emits the message to stdout
  without committing; `--single` (`--no-decompose`) produces exactly one message
  with no multi-commit decomposition. `stagecoach` produces ONLY the bare
  descriptive message. **The pipeline retains ownership of the commit itself** —
  the snapshot-based atomic plumbing commit (§5.1: `write-tree` / `commit-tree` /
  CAS `update-ref`), `restore_critical_files`, ARG_MAX-safe staging, the
  commit-gen retry/fallback, and the **task-prefix position layer** (§5.1
  "Commit Message Format"). `stagecoach`'s stdout is fed to
  `formatCommitMessage`, which layers the position prefix and commits, adding
  **no trailer** (§5.1, §9.10.2).
- **Provider/harness routing.** `stagecoach` is invoked with the resolved
  provider (`pi` | `claude-code`) and model forwarded from the pipeline's
  resolved config (§9.2 / `.hack`), so `stagecoach` generates via the same
  backend the pipeline uses for agent runs. "Everything else is exactly what
  `stagecoach` does by default": its own style/format selection, anti-duplicate,
  and retry discipline apply. `PRP_COMMIT_STYLE` (§5.1), if set, is forwarded as
  `stagecoach`'s `--format` (`auto` | `plain` | `conventional` | `gitmoji`);
  unset, `stagecoach`'s native default (`auto`, learned from history) applies.
- **Determinism contract.** Everything outside the generated message **text** is
  deterministic: staging, the atomic commit, the position prefix, and the commit
  identity. Only the descriptive-message wording is model-generated, and that is
  `stagecoach`'s responsibility. **There MUST NEVER be a hardcoded attribution,
  trailer, or footer anywhere in this pipeline's commit path.**
- **Supersedes the in-process agent.** The previous in-process "stagecoach LLM
  commit-message agent" (`commit-message-agent.ts`) and its style-learning
  machinery are removed in favor of this delegation. `stagecoach`'s own output
  discipline (emit only the message; no prefix, no banner, no trailer) replaces
  the in-process rules.

**Acceptance criteria.**

- A work-item commit authored by the pipeline carries **no** `Co-Authored-By:`
  trailer, no `Generated-by` footer, and no machine author — verifiable by
  `git log --format='%B' <sha>` containing none of those tokens.
- The commit message is produced by an actual `stagecoach` child process
  (observable in a verbose/trace run as a `stagecoach --dry-run --single`
  invocation), not by an in-process LLM agent.
- `npm install` of this package makes `stagecoach` resolvable from the
  dependency tree with no separate install step and no `PATH` dependency.
- Removing the `stagecoach` binary at runtime produces a clear, actionable
  error (not a silent fallback to an in-process generator).

#### 9.10.2 Commit-Identity Structural Guard

**Problem.** §5.1 "Commit-identity transparency" already forbids any
`Co-Authored-By:` trailer, machine author, or identity injection. Incident (1)
showed a hardcoded `Co-Authored-By: Claude <noreply@anthropic.com>` literal
violating that requirement on every work-item commit — a behavioral requirement
with **no enforcement** regressed the moment it was written. The existing §5.1
wording even contained a loophole ("…unless an explicit style layer below adds
one") that permitted the trailer; that loophole is closed.

**Requirement — behavioral.** `formatCommitMessage` (and the whole commit path)
MUST NEVER emit a `Co-Authored-By:` trailer, a `Generated-by`/`Generated with`
footer, a machine/branded author, or any identity injection — in any mode
(task-prefix, plain, non-backlog, fallback). §5.1's "unless an explicit style
layer below adds one" carve-out is **removed**: no style layer may add a
`Co-Authored-By` trailer, ever.

**Requirement — structural enforcement (self-source-scan test).** Mirroring
`stagecoach`'s FR-39a discipline, a test MUST walk all **production** source
under `src/` (and `cmd/` if present), **skipping** any path ending in
`_test.go`/`.test.ts`/`.spec.ts` and the guard's own file, and FAIL the build if
any **non-comment** line contains a forbidden identity/attribution signal as a
string literal:

- the trailer tokens: `Co-Authored-By`, `Co-Authored`, `coauthor` (case-
  insensitive), and the specific cargo-culted strings `noreply@anthropic.com`,
  `Generated with [Claude Code]`, `🤖 Generated`;
- the git-identity env literals `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`,
  `GIT_AUTHOR_DATE`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`,
  `GIT_COMMITTER_DATE`;
- identity-config writes signalled by the string literals `user.name` /
  `user.email` appearing as arguments to a git-config call in a non-comment line.

Comment lines (`//`, `/* … */`, `*`-prefixed JSDoc) are skipped so doc citations
of the incident do not self-trip; the test MUST assert it visited `> 0`
production files (so a path-resolution bug cannot pass vacuously). The guard
targets call-site string literals, not bare substrings inside comments.

**Requirement — behavioral test.** The prior test that locked in the bug
(`PRESERVES the Co-Authored-By trailer in EVERY output`) is replaced by its
inverse: `formatCommitMessage` is asserted — across task-prefix, plain, and
non-backlog (`null`-position) modes, plus the `[PRP Auto]`-strip path — to
contain **no** `Co-Authored-By`, **no** `noreply@anthropic.com`, and no
`[PRP Auto]` banner.

**Acceptance criteria.**

- The self-source-scan reports **zero** forbidden hits on the current tree.
- The self-source-scan **fires** when a forbidden literal (e.g. a
  `Co-Authored-By` string, or an `os.environ['GIT_COMMITTER_NAME']` /
  `git config user.name` write) is temporarily injected into a production file,
  then reverts green when removed (verified in the implementing PRP).
- `formatCommitMessage` unit/integration tests assert trailer/banner ABSENCE
  (not presence) in every mode.
- No comment-line citation of the incident causes a false failure.

#### 9.10.3 Agent Tool-Access Scoping & Remote-Mutation Prohibition

**Problem (incident 2 root cause).** The pipeline exposed an **unguarded** `bash`
execution tool to the agent: `spawn(command, { shell: true })` =
`/bin/sh -c "<anything>"`, with **no command allowlist, no denylist, no sandbox**
— only a timeout. The host had `gh` authenticated to github.com as the repo
owner with **`repo`** scope (which covers default-branch changes). A `pi`+`glm`
agent used that shell to change the target repository's GitHub default branch to
the test worktree's branch (proven by the cached `origin/HEAD -> origin/hack`).
`pi`'s own GitHub tool only **reads** the default branch; raw shell + the
authed `gh` was the vector. The exact command was not logged (agent bash calls
bypass the interactive shell history), so the mitigation removes the
**capability** regardless of wording.

**Requirement — per-role tool matrix.** Agent tool access is **scoped by role**,
not granted universally:

| Role                       | `bash` tool         | structured `git` tools                      | Rationale                                                                                |
| -------------------------- | ------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Research / Planner / Coder | **none**            | read-only (`git_status`, `git_diff`) only   | these roles research/implement; they must not mutate git state or run arbitrary shell    |
| Commit agent               | **none**            | `git_commit` only (structured; no raw bash) | committing is a structured operation, never raw shell                                    |
| Validation agent           | **yes, denylisted** | —                                           | MUST run the test gates (`tsc` / `vitest` / smoke); shell is required but fenced (below) |

**Requirement — bash denylist (validation agent).** The bash tool MUST refuse —
non-zero exit, clear error — any command that matches a repo-remote-mutating or
default-branch-mutating operation before exec. The denylist matches (case-
insensitive, on the command string):

- `git push`, `git remote` (any subcommand), `git update-ref`, `git config`,
  `git reset --hard` against a shared ref, `git rebase`, `git commit` (the bash
  tool is not a commit path; structured `git_commit` is);
- `gh repo` (any subcommand), `gh api -X PATCH|POST|DELETE`, and any
  `gh api … default_branch`;
- `curl` / `wget` to `api.github.com`, and any reference to `default_branch`.

Ambiguous matches **fail closed** (refuse). The denylist is evaluated on the raw
command string prior to spawn; it is not advisory.

**Requirement — universal prohibition (all agents, all roles).** Repo-remote-
mutating operations — `git push`, `git remote`, `git update-ref`, `gh repo`,
GitHub-API writes, and default-branch mutation — are **never exposed as any
agent tool, in any role**. These are **human-only** operations, and this rule is
added to the §5.2 "Universal Forbidden Operations." The structured `git` tools
(`git_status` / `git_diff` / `git_add` / `git_commit`) are the **only** git
surface any agent receives, and none of them can reach a remote or the default
branch. Where an agent needs git, it uses these structured tools; it MUST NOT
reach git through the bash tool.

**Acceptance criteria.**

- A research/planner/coder agent's tool set contains **no** `bash` tool and no
  `git_*` tool beyond `git_status` / `git_diff`.
- The commit agent's tool set contains no `bash`; it commits only via the
  structured `git_commit` tool.
- The validation agent's `bash` tool refuses `git push`, `gh repo edit
--default-branch <x>`, and `gh api -X PATCH repos/…/… -f default_branch=…`
  with a fail-closed error, while still running `npx vitest run` / `npm test` /
  `npx tsc --noEmit`.
- No agent tool, in any role, can change a remote ref or the repository default
  branch.
- Re-running the scenario that flipped the default branch (an agent attempting
  `gh repo edit … --default-branch …` or equivalent) now fails at the tool layer
  before any GitHub API call is made.
